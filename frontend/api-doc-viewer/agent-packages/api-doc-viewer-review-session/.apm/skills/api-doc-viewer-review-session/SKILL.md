# Reviewing an api-doc-viewer session

Use this after finishing a non-trivial task in this repository — on request,
or proactively before ending a session that involved real exploration,
debugging, or back-and-forth with the user.

## First instruction

Review the conversation just completed. Look for anything that was
unexpected, not obvious, hard to infer from the request as stated, or where
actual repo/tool behavior diverged from what the docs (or your own working
assumptions) implied — in either direction: the request harder to pin down
than expected, or the codebase/tooling behaving differently than documented.
Summarize those findings for the user, then update the relevant agent skill
doc(s) if the findings are durable and generalizable to future sessions — not
one-off task trivia.

## What counts as a finding worth recording

- **Requirement ambiguity** that took a clarifying question (or a wrong first
  attempt) to resolve — e.g., a request enumerating a few example cases when
  the actual intent was a full combination matrix; a compound ask ("X, plus Y
  variants of X") that turned out to need descoping once the user weighed in.
- **A skill/doc claim that doesn't match the current repo state** — a stale
  filename, a wrong id-derivation example, an outdated generator boundary.
  Verify with `Read`/`Grep`/`ls`/`find` before writing anything down: "the
  skill says X" is not the same as "X is true now."
- **A generator/tool behavior that surprised you** — destructive full-tree
  regeneration, append-only case numbering, a hidden scope boundary (e.g.
  only a handful of sample subdirectories are actually auto-generated, the
  rest need hand-wiring), a config name that implies something false (a
  "legacy" test config that still has the same hard dependency as the
  primary one).
- **An environment limitation that changed how you had to verify work** —
  e.g. a required tool (Docker, a database, a network service) wasn't
  available, so the normal verification path was unavailable and a
  substitute method was needed.
- **A process trap of your own** — e.g. bundling several clarifying
  questions when the user actually wanted to renegotiate scope first; nearly
  editing a generated/deployed copy of a doc instead of its canonical source.

Skip: things fully explained by reading the code once, one-off content/value
choices specific to this task, anything already correctly documented.

## Verifying before writing anything down

Every finding must be checked against the live repo, not asserted from
memory, from the skill text, or from what the conversation *assumed*
happened:

- Confirm file, filename, and id claims with `Read`/`Grep`/`ls`/`find`
  against the actual working tree — not against a skill's prose.
- For anything Storybook-related, prefer a freshly built `index.json` (or a
  live browser check) over guessing a story id from a filename or title —
  titles and filenames can diverge (see the `api-doc-viewer-testing` skill's
  *Meta id prefix vs. folder name* note for a concrete example of this).
- When two sources disagree (a skill doc vs. the actual file tree; the
  conversation's stated assumption vs. `git diff`/build output), trust the
  live repo state, and treat the mismatch itself as a finding.

## Design first, then skills

`docs/design/` is the source of truth; skills derive from it. A finding about **behaviour**
(what is displayed, a diff rule, an architecture boundary) goes into the matching design file
first — `docs/design/<api-type>/display-coverage.md`, `features/`, or `architecture/` — and the
skill then references it. Findings about **process** (traps, tooling, verification) go into skills
only. A dated review or decision record goes to `docs/design/<api-type>/notes/<yyyy-mm>-<topic>.md`.

## Updating the docs — canonical source, not the deployed copy

**Do not edit `.claude/skills/*`, `.claude/rules/*`, `.cursor/skills/*`, or
`.cursor/rules/*` directly.** Those trees are gitignored and wholly
regenerated by APM from `agent-packages/<package>/.apm/...` — a hand-edit
there is never committed and is silently overwritten by the next install.

1. Find the canonical source: `agent-packages/<package>/.apm/skills/<package>/SKILL.md`
   (or the matching `.apm/instructions/<package>.instructions.md` for the
   auto-suggest rule shown as a system reminder).
2. Edit the canonical file(s) there.
3. Resync deployed copies from the repo root:
   `apm install --target cursor,claude --legacy-skill-paths`.
4. Verify the sync — diff the canonical file against its `.claude/skills/...`
   counterpart; they must be identical after install.
5. `git status` should then show only `agent-packages/**` and `apm.lock.yaml`
   changed. If `.claude/` or `.cursor/` paths show up in `git status`, they
   are not meant to be tracked — re-check `.gitignore` before committing.

## Reporting the review

Summarize findings for the user before or alongside making doc edits — don't
silently rewrite skills. For each finding, state: what was surprising, the
evidence (file path, command output, or quoted conversation text), and what
(if anything) you changed as a result. If a finding turns out to be genuinely
one-off task trivia once you look closer, say so and skip documenting it
rather than padding a skill with noise.
